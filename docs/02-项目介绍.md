# Personal RAG 项目介绍

## 1. 项目一句话介绍

Personal RAG 是一个面向个人 PDF 资料的本地知识库：用户上传 PDF 后，系统完成解析、切块、中文向量化和持久化检索，再由 DeepSeek 基于检索资料生成带来源的流式回答。

## 2. 项目目标

直接把整本 PDF 交给大模型存在上下文过长、成本高、回答来源不清楚等问题。本项目通过 RAG 只取与问题最相关的少量文本块，让模型在有限上下文中基于资料回答。

核心目标：

- 支持 PDF 上传、管理和删除。
- 支持中文语义检索，而不只是关键词匹配。
- 回答尽量忠于知识库，并返回文件与页码来源。
- 支持流式输出，改善首字等待体验。
- 前后端分离，代码职责清晰，便于继续扩展。

## 3. 技术栈

| 层次 | 技术 | 作用 |
|---|---|---|
| 前端 | HTML、Tailwind CSS、原生 JavaScript | 上传、文档管理、流式聊天 |
| API | FastAPI、Pydantic、Uvicorn | 接口、校验、Swagger、流式响应 |
| LLM | DeepSeek Flash、LangChain | Agent、RAG Prompt、回答生成 |
| 文档 | PyPDFLoader | 按页提取 PDF 文字与 metadata |
| 切块 | RecursiveCharacterTextSplitter | 将页面切成可检索 chunks |
| Embedding | BAAI/bge-small-zh-v1.5 | 中文文本转 512 维向量 |
| 向量库 | Chroma | 保存 chunks、向量和 metadata，执行相似度检索 |
| 管理库 | SQLite | 保存文档 ID、路径、页数、chunk 数等目录信息 |

## 4. 前后端架构

```text
frontend/
└── index.html
    ├── PDF 上传
    ├── 文档列表与删除
    └── 流式 RAG 聊天

backend/
├── main.py                 FastAPI 接口入口
├── schemas.py              请求和响应模型
├── config.py               项目路径与运行目录
├── agent_service.py        Agent、DeepSeek 和流式生成
├── document_service.py     PDF 保存、解析和切块
├── vector_store_service.py Embedding 与 Chroma 检索
└── database_service.py     SQLite 文档管理

data/
├── uploads/                原始 PDF
├── chroma_db/              向量索引
└── knowledge.db            文档目录
```

整理原则：

```text
前端只负责页面和请求
main.py 集中展示接口，便于初学者阅读
service 文件按功能拆分，避免 main.py 过长
data 集中存放所有运行数据
```

## 5. PDF 入库流程

```text
UploadFile
  ↓
UUID 生成 document_id
  ↓
原始 PDF 保存到 data/uploads
  ↓
PyPDFLoader 按原始页面生成 Documents
  ↓
RecursiveCharacterTextSplitter
  chunk_size=500，chunk_overlap=50
  ↓
为每个 chunk 添加 document_id、source、page、chunk_index
  ↓
BGE 生成 512 维向量
  ↓
Chroma 保存 ID、chunk 原文、向量和 metadata
  ↓
SQLite 保存文档目录
```

`full_text` 只用于字符统计和 Swagger 预览；真正参与向量化的是 `chunks`。

## 6. RAG 问答流程

```text
用户问题
  ↓
BGE 将问题转换成同维度向量
  ↓
Chroma 计算向量距离，返回 Top-K chunks
  ↓
系统将 chunks 组合成参考资料
  ↓
参考资料 + 用户问题交给 DeepSeek
  ↓
DeepSeek 生成回答
  ↓
astream + StreamingResponse 逐块返回
```

三者分工：

- BGE：把文本翻译成向量。
- Chroma：比较并检索向量。
- DeepSeek：阅读检索文本并组织答案。

## 7. 数据设计

### Chroma 记录

```text
ID: {document_id}-chunk-{index}
page_content: chunk 原文
embedding: 512 维向量
metadata:
  document_id
  source
  page
  chunk_index
```

### SQLite documents 表

```text
id             文档 UUID
filename       原始文件名
file_path      原始 PDF 路径
pages          页数
characters     字符数
chunk_count    切块数
created_at     上传时间
```

原始 PDF 是事实来源，SQLite 是管理目录，Chroma 是可重建的检索索引。

## 8. 主要接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/` | 后端健康检查 |
| POST | `/upload` | 上传、解析、切块并入库 |
| GET | `/documents` | 查看知识库文档 |
| DELETE | `/documents/{id}` | 删除 PDF、SQLite 记录和 Chroma chunks |
| POST | `/search` | 只检索，不调用 LLM |
| POST | `/rag` | 完整 JSON RAG 回答和来源 |
| POST | `/rag/stream` | 流式 RAG 回答 |
| POST | `/chat` | 不使用知识库的普通 Agent |
| POST | `/chat/stream` | 普通 Agent 流式回答 |

保留 `/search` 的原因是可观察性：可以单独判断问题出在检索还是生成阶段。

## 9. 项目实现思路

本项目不是一次性堆出成品，而是按可验证链路逐步实现：

1. 先实现最小 Agent，理解 Model、Message、Tool。
2. 接入 FastAPI，理解请求模型和响应模型。
3. 加入同步、异步与流式输出。
4. 单独验证 PDF 解析，不急着做 RAG。
5. 单独验证文本切块及 overlap。
6. 用三句话验证 BGE Embedding 和语义相似度。
7. 用三句话验证 Chroma 检索。
8. 再连接 PDF chunks、持久化 Chroma和 `/search`。
9. 最后把检索内容交给 DeepSeek，形成 RAG。
10. 增加原始文件、SQLite 管理和独立前端。

这种思路的价值是：每一步输入输出明确，出现问题时能快速定位，不会把 PDF、Embedding、向量库和大模型错误混在一起。

## 10. 面试中的项目表述

### 30 秒版本

> 我实现了一个前后端分离的个人 PDF RAG 知识库。后端使用 FastAPI 和 LangChain，PDF 经 PyPDFLoader 解析后用递归切块器拆分，再由本地 BGE 中文模型生成向量并持久化到 Chroma。提问时系统进行 Top-K 相似度检索，将相关文本和页码作为上下文交给 DeepSeek，并通过 StreamingResponse 流式返回。原始文件保存在本地，SQLite 管理文档目录，支持文档查看和级联删除。

## 11. 当前边界

- 仅支持有文字层的 PDF，不含 OCR。
- BGE 在 CPU 本地运行，首次加载较慢。
- `InMemorySaver` 只提供进程内会话记忆。
- 当前没有相关度阈值与 Reranker。
- ID 和入库事务仍可进一步增强。
- 单机 SQLite/Chroma 适合个人项目，不面向大规模并发。

这些不是需要隐藏的问题，而是面试中展示工程判断和后续规划的切入点。
