# Personal RAG 复盘总结

## 1. 项目制作路线

这个项目没有一开始就直接编写完整 RAG，而是按照“每次只增加一个新知识点”的方式逐步完成：

```text
1. 创建最简单的 Agent
   ↓
2. 给 Agent 加入 Message、工具和会话记忆
   ↓
3. 使用 FastAPI 提供聊天接口
   ↓
4. 增加普通调用和流式调用
   ↓
5. 上传并保存 PDF
   ↓
6. 使用 PyPDFLoader 按页提取文字
   ↓
7. 使用 RecursiveCharacterTextSplitter 切分文本
   ↓
8. 使用 BGE 将 chunks 转换成向量
   ↓
9. 将 chunks、向量和 metadata 存入 Chroma
   ↓
10. 根据用户问题检索相关 chunks
   ↓
11. 把检索内容和问题一起交给 DeepSeek
   ↓
12. 通过 astream 和 StreamingResponse 流式返回答案
   ↓
13. 使用 SQLite 管理文档信息和删除操作
   ↓
14. 添加前端页面并整理项目目录
```

每个阶段都先单独测试，确认输入和输出正确后，再进入下一步。例如，先确认 PDF 可以提取文字，再学习切块；先确认 Embedding 能生成向量，再接入 Chroma。这样出现问题时，可以判断错误到底来自 PDF、切块、向量化、检索还是大模型。

面试时可以这样概括制作思路：

> 我先实现了一个最小 Agent，理解模型、消息、工具和记忆；然后使用 FastAPI 将它封装成接口，并加入流式输出。接着实现 PDF 上传和文字解析，把文本切成 chunks，使用本地 BGE 模型生成向量并存入 Chroma。用户提问时，系统先检索相关 chunks，再把资料交给 DeepSeek 生成答案。最后补充 SQLite 文档管理、删除功能和独立前端，形成完整的个人 RAG 知识库。

## 2. 最终完成了什么

项目从最小 Agent 演进为一个可运行的个人 RAG 系统，完成：

- 普通 Agent 与工具调用观察。
- FastAPI JSON、流式接口和 Swagger。
- PDF 上传、保存、解析和按页 metadata。
- 递归文本切块与 overlap。
- 本地中文 BGE Embedding。
- Chroma 持久化、检索和按文档删除。
- DeepSeek 普通/流式 RAG 回答与来源返回。
- SQLite 文档目录与原始 PDF 生命周期管理。
- 独立前端的上传、文档管理和流式聊天。

## 3. 最重要的认知

### RAG 不是“把 PDF 发给大模型”

标准链路是：

```text
Retrieval 检索
+ Augmented 上下文增强
+ Generation 大模型生成
```

最小 RAG 在 `/rag` 完成时已经成立；流式输出、Agent 路由和前端属于体验与工程增强。

### 向量、ID 和 metadata 不同

- 向量描述语义，用于相似度搜索。
- ID 唯一标识数据库记录，用于更新和删除。
- metadata 描述来源、页码和 chunk 编号，用于过滤和引用。

向量不是 ID，也不是人工分类标签。

### Chroma 不应该是一手资料库

正确分工：

```text
原始 PDF：事实来源
SQLite：管理目录
Chroma：可重建索引
```

如果资料内容错误，应修改或替换原始 PDF，再重新索引；只修改 Chroma 会造成数据不一致。

## 4. 关键技术取舍

### 为什么选择 RecursiveCharacterTextSplitter

它先尝试段落、换行和空格等自然边界，仍过长时才递归到更细粒度。配置 `chunk_size=500`、`chunk_overlap=50`，用少量重复降低句子跨边界造成的信息损失。

不足是默认分隔符对中文标点不够敏感，后续可显式加入 `。！？；，` 或使用语义切块。

### 为什么选择本地 BGE

- 对中文检索友好。
- MIT 许可证，无按次 API 费用。
- 数据无需发送给第三方 Embedding 服务。
- 小型模型适合个人电脑演示。

代价是本地模型下载、磁盘占用和 CPU 启动时间。

### 为什么保留 `/search`

如果 RAG 回答错误，原因可能是：

```text
PDF 没解析好
切块不合理
检索没有命中
Prompt 约束不足
LLM 生成偏离资料
```

独立 `/search` 可以直接观察 Top-K chunks，把检索问题与生成问题分开定位。

### 为什么前后端分离

早期将 HTML 直接挂在 FastAPI 上便于快速验证，但功能增加后职责混杂。最终拆分后：

- 前端独立负责交互与流式渲染。
- 后端只提供 JSON/文本 API。
- CORS 明确跨域边界。
- 将来可以替换 Vue/React 而不改 RAG 核心。

## 5. 遇到的问题与解决方法

### API Key 未读取

原因是只有 `.env.example`，没有 `.env`。通过 `load_dotenv` 从项目根目录读取，并将真实 Key 排除在 Git 之外。

经验：配置文件、工作目录和进程重启是后端排错的第一层。

### Uvicorn 命令找不到

改用：

```powershell
.venv\Scripts\python.exe -m uvicorn backend.main:app --reload
```

经验：使用虚拟环境 Python 的模块调用，比依赖全局 PATH 更稳定。

### 本地模型重复联网检查

模型下载完成后，正式后端设置 `local_files_only=True`，避免受限网络下反复 HEAD 请求；首次下载由独立 Embedding 示例完成。

### `documents`、`full_text`、`chunks` 容易混淆

最终明确为两条支路：

```text
documents → full_text → 字符统计和预览
documents → chunks → Embedding 和 Chroma
```

### 老版本向量无法按文档删除

早期 ID 使用文件名且缺少 `document_id`。后续改为 UUID 文档 ID，并写入 SQLite 和所有 chunk metadata。

经验：任何需要更新、删除的数据都应该在设计早期拥有稳定主键。

## 6. 做得好的地方

- 按单一知识点逐步验证，降低学习和排错负担。
- PDF、Embedding、Chroma、LLM 均有独立测试阶段。
- 原始文本和来源 metadata 随向量一起保存。
- 普通接口与流式接口并存，便于理解和调试。
- 文档删除同时清理文件、SQLite 和 Chroma。
- 前后端分开，后端服务按功能平铺，结构简单且便于学习。

## 7. 仍需改进的地方

### 数据一致性

当前上传包含文件保存、Chroma 入库和 SQLite 写入三个步骤，任何中途失败都可能留下部分数据。可以增加补偿逻辑或任务状态：

```text
processing → ready / failed
```

### 检索质量

当前直接取 Top-K，没有相关度阈值。无关问题也会返回“最接近但仍不相关”的 chunks。可以增加：

- 相似度阈值。
- MMR 降低重复结果。
- BGE Reranker 二次排序。
- 不同 chunk_size/overlap 的离线评估。

### 文档能力

- OCR 支持扫描 PDF。
- 支持 DOCX、Markdown、TXT。
- 文件哈希去重。
- 文档版本和重新索引。

### 会话与用户

- 将 thread_id 暴露给前端。
- 使用持久化 checkpointer。
- 用户鉴权和知识库隔离。

### 流式协议

当前流式接口返回纯文本，来源由额外 `/search` 获取。生产版本可以使用 SSE，分别发送 answer、source、done 和 error 事件。

## 8. 如果重新做一次

1. 先定义 Document、Chunk、Conversation 三种核心实体。
2. 第一版就使用稳定 `document_id`。
3. 把原始资料视为事实来源，把向量库视为派生索引。
4. 从一开始保留 `/search` 和可观察日志。
5. 在功能稳定后再做前端，避免 UI 掩盖后端问题。
6. 用固定的测试问题集记录检索结果，防止参数调整后回退。

## 9. 面试常见追问

### 为什么不直接把整个 PDF 放进 Prompt？

文档可能超过上下文限制，并增加延迟和成本。RAG 只提供与问题相关的少量 chunks，也更容易追踪来源。

### Embedding 模型和 DeepSeek 有什么区别？

BGE 负责把文本编码成向量；DeepSeek 负责理解上下文并生成自然语言。Chroma 负责向量比较。

### chunk_size 和 overlap 如何确定？

当前 500/50 是学习阶段的起点，不是通用最优值。正式优化应结合文档结构、模型上下文和检索评估，用测试集比较命中率与重复度。

### 如何降低幻觉？

- Prompt 要求只根据资料回答。
- 返回来源供用户核查。
- 增加相似度阈值，无相关资料时拒答。
- 对检索结果进行 Rerank。
- 建立 RAG 评估集。

### 如何删除错误信息？

根据 `document_id` 删除 Chroma chunks、原始 PDF 和 SQLite 记录；修改原始资料后重新入库。仅删除向量中的某一段会与事实来源不一致。

### 为什么使用 SQLite 和 Chroma 两个数据库？

SQLite 擅长结构化管理和精确查询；Chroma 擅长语义向量检索。让不同存储承担适合的职责，避免把向量库当成万能数据库。

## 10. 下一阶段路线

优先级建议：

1. 相关度阈值和无答案拒答。
2. 文件哈希去重与入库状态。
3. SSE 同时传答案和来源。
4. Reranker 与检索评估。
5. OCR 和多格式文档。
6. 持久化会话、用户隔离和部署。

## 11. 个人收获表述

> 这个项目让我真正理解了 RAG 不是简单调用大模型，而是一条包含数据解析、切块、Embedding、索引、检索、上下文构造和生成的工程链路。我也认识到向量库是可重建索引，原始资料和业务元数据需要独立管理。通过将每一步拆开测试，我建立了定位 RAG 问题的方法：先看解析，再看 chunks，再看检索，最后看生成。
